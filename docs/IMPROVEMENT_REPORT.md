# DLSS5 工具 改进报告

从最初的 Python 版本到当前的 GPU 直通 + 双缓冲架构

---

## 摘要

| 指标 | 起点 (test4) | 现在 | 提升 |
|---|---|---|---|
| 720p 单帧 | 21.8 ms (46 fps) | **5.2 ms (193 fps)** | **4.2x** |
| 1080p 单帧 | 未直接基准(外推约 30+ ms)¹ | **9.5 ms (105 fps)** | — |
| 720p 导出 | 受双重拖累,未单独基准¹ | **~150 fps** | — |
| 1080p 导出 | 慢且界面冻结 | **91-94 fps** | — |
| GPU 利用率 | 87-88%(且大量 CPU 空转) | **98%** | — |
| 导出时界面 | 完全冻结 | 全程可交互 | — |

> ¹ 起点版本只在 720p 做了完整逐阶段基准(21.76 ms/帧)。
> 其导出还受「主线程冻结 + `cv2.VideoWriter(mp4v)` 软编码」双重拖累,
> 当时未做独立导出基准,故不列具体数字 —— 可确定的是处理单帧就要 21.8 ms,
> 编码再串行叠加其后,且全程界面无响应。

**一句话总结**:把「CPU 搬运 + numpy 转换 + 逐帧同步等待」这条链路整体拆掉，
换成「宿主直接吃 BGR / 直接吐 RGBA + 资源全程复用 + 双槽位流水线」，
并用 ffmpeg 硬件编码管线替换 `cv2.VideoWriter`。

**两个关键的"停止点"**(不是所有优化都值得做):

1. **双缓冲已经是最优,三缓冲无收益** —— 实测吞吐完全相同(见[分支 D](#分支-d三缓冲深队列))。
   吞吐 = `max(CPU每帧, GPU每帧)`,缓冲深度只缓冲吞吐、不创造吞吐。
2. **剩余瓶颈是 GPU 功耗墙** —— `SW Power Cap: Active`,时钟只跑到上限的 81%,
   而温度仅 70 °C。继续优化代码已无空间。

## 阶段 0：起点 —— 原始 Python 版

### 架构

```
                       ┌──────────────────────────────────┐
                       │        Python 主线程             │
                       │        (tkinter 界面)            │
                       └───────────────┬──────────────────┘
                                       │ 用户点"导出"
                                       ▼
   ┌───────────────────────────────────────────────────────────────┐
   │  主线程 for 循环(界面在此完全冻结)                            │
   │                                                               │
   │   cv2.VideoCapture.read()                                     │
   │            │  BGR  (H×W×3)                                    │
   │            ▼                                                  │
   │   cv2.cvtColor(BGR→RGB)          ~0.6 ms   ← CPU              │
   │            │                                                  │
   │            ▼                                                  │
   │   np.dstack([rgb, alpha=255])    ~3.6 ms   ← CPU 大拷贝       │
   │            │  RGBA (H×W×4)                                    │
   │            ▼                                                  │
   │   ┌────────────────────────────────────────┐                  │
   │   │  dlssnr_host.dll  (旧宿主)             │                  │
   │   │                                        │                  │
   │   │   mv = np.zeros(...)  ← 每帧在 CPU 分配│  ~16.1 ms        │
   │   │   dp = np.zeros(...)  ← 每帧在 CPU 分配│                  │
   │   │   o  = np.zeros_like() ← 每帧分配      │                  │
   │   │                                        │                  │
   │   │   [CPU] 逐像素 BGR↔RGBA 转换           │                  │
   │   │        │                               │                  │
   │   │        ▼                               │                  │
   │   │   [CPU→GPU] 上传缓冲                   │                  │
   │   │        │                               │                  │
   │   │        ▼                               │                  │
   │   │   [GPU] Feature 18 推理                │                  │
   │   │        │                               │                  │
   │   │        ▼                               │                  │
   │   │   [GPU→CPU] 回读                       │                  │
   │   │                                        │                  │
   │   │   分 3 段提交命令,每段各等一次围栏  ← 同步开销大          │
   │   │   命令分配器/命令列表 每帧重建       ← 分配开销           │
   │   └────────────────────────────────────────┘                  │
   │            │  RGBA                                            │
   │            ▼                                                  │
   │   cv2.cvtColor(RGBA→BGR)         ~4.0 ms   ← CPU              │
   │            │                                                  │
   │            ▼                                                  │
   │   np.clip(ff + (fo-ff)*mix)      ← 输出视图,基于 float32     │
   │            │                                                  │
   │            ▼                                                  │
   │   cv2.VideoWriter(mp4v)          ← 软编码, 质量差            │
   │   self.root.update()             ← 唯一让界面"呼吸"的手段    │
   └───────────────────────────────────────────────────────────────┘
```

### 实测每帧开销(720p)

| 阶段 | 耗时 | 占比 |
|---|---|---|
| cvtColor BGR→RGB | 0.58 ms | 2.4% |
| **np.dstack(alpha)** | **3.57 ms** | 14.5% |
| 旧宿主(含内部往返) | 16.14 ms | 65.5% |
| numpy 缓冲分配 | 0.36 ms | 1.5% |
| **cvtColor RGBA→BGR** | **4.00 ms** | 16.2% |
| **合计** | **24.65 ms (40.6 fps)** | |

> 独立进程精确测量旧路径全流程为 **21.76 ms/帧 (46.0 fps)**。

### 问题清单

1. **CPU 侧 8.5 ms(34.5%)纯属浪费** —— `dstack` 和两次 `cvtColor` 都只是为了让数据在
   Python 的通道序约定和宿主的通道序约定之间来回转换。
2. **每帧都在分配 numpy 数组** —— `mv`/`dp`/`o` 三个大数组,而内容永远是零。
3. **每帧三次同步等待** —— 上传、推理、回读各提交一次命令、各等一次围栏。
4. **每帧重建 D3D12 对象** —— 命令分配器、命令列表反复创建销毁。
5. **导出在主线程** —— 界面完全冻结,只能靠 `root.update()` 勉强重绘。
6. **编码器是 `cv2.VideoWriter(mp4v)`** —— 软编码,速度慢,画质差,无法选编码器。

## 阶段 1：先测量,不猜 —— 瓶颈定位

在动手改之前,先把每一段拆开计时,避免"优化了不重要的地方"。

```
   ┌─────────────────────────────────────────────────────┐
   │  测量方法:                                          │
   │    • Python 侧: time.perf_counter() 包住每个调用    │
   │    • C 宿主侧: QPC(QueryPerformanceCounter)打点     │
   │      写入 host2_perf.txt(仅当 host2_perf.on 存在)  │
   │    • 显卡侧:   nvidia-smi 轮询                      │
   └─────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌─────────────────────────────────────────────────────┐
   │  结论: CPU 链路 8.5ms / 总 24.65ms = 34.5%          │
   │                                                      │
   │  → 优化目标明确: 干掉 CPU 链路 + 压缩宿主内部往返   │
   └─────────────────────────────────────────────────────┘
```

**这一步的价值**:它告诉我们"GPU 推理只占 65%",所以**单靠等硬件是没用的**,
必须先把 35% 的 CPU 浪费消灭掉。后面所有改动都围绕这两点:

- 让宿主**直接接受 BGR**(cv2 的原生格式),**直接输出 RGBA**(下游需要什么就给什么)
- 让宿主的 D3D12 资源**全程复用**,每帧只提交一次、只等一次

## 阶段 2：GPU 直通宿主

### 为什么必须重写宿主,而不是改 Python

旧宿主的接口是:

```c
int dlssnr_process(uint8_t* inRgba, float* mv, float* dp, uint8_t* outRgba, int reset);
//                     ↑ RGBA            ↑ 零  ↑ 零        ↑ RGBA
```

四个 **CPU 指针** —— 这个签名本身就决定了「数据必须待在 CPU 内存里」,
宿主内部无论如何都要做 CPU↔GPU 往返。**改 Python 侧治标不治本,必须换接口。**

### 新宿主设计

```c
int dlssnr2_init(int w, int h, const wchar_t* logPath);
int dlssnr2_process_rgba(uint8_t* inBgr, uint8_t* outRgba, int reset);
//                          ↑ BGR          ↑ RGBA
```

只留两个 Buffer,**两端的转换都被搬进宿主内部,且用 SIMD 一次做完**。

### 新工作流

```
   cv2.VideoCapture.read()
            │  BGR (H×W×3)  ← 不再转换,直接交给宿主
            ▼
   ┌──────────────────────────────────────────────────────────────┐
   │  dlssnr_host2.dll                                            │
   │                                                              │
   │  ① [CPU] SSSE3 SIMD: BGR → RGBA + alpha=255                  │
   │        一次处理 4 像素(12B → 16B)                           │
   │        _mm_shuffle_epi8 通道交换 + _mm_or 补 alpha           │
   │        ≈ 0.36 ms  (对比 numpy dstack 的 3.57 ms)            │
   │            │                                                 │
   │            ▼  写入常驻的 uploadBuf(Map/Unmap 复用)           │
   │                                                              │
   │  ② [GPU] 单个命令列表,一次录制完成:                         │
   │        ┌─ 屏障 COMMON → COPY_DEST                            │
   │        ├─ CopyTextureRegion (uploadBuf → texIn)              │
   │        ├─ 屏障 → NON_PIXEL_SHADER_RESOURCE                   │
   │        ├─ 屏障 texOut → UNORDERED_ACCESS                     │
   │        ├─ NGX EvaluateFeature(Feature 18)  ← 真正的推理      │
   │        ├─ 屏障 texOut → COPY_SOURCE                          │
   │        ├─ CopyTextureRegion (texOut → readbackBuf)           │
   │        └─ 全部屏障复位回 COMMON(供下一帧直接复用)            │
   │            │                                                 │
   │            ▼  一次 ExecuteCommandLists + 一次围栏等待        │
   │                                                              │
   │  ③ [CPU] RGBA 直出: memcpy(readbackBuf → outRgba)            │
   │        零通道转换(旧版这里要花 4.0 ms 做 RGBA→BGR)          │
   └──────────────────────────────────────────────────────────────┘
            │  RGBA (H×W×4)  ← 下游(PIL / ffmpeg)需要的正是这个
            ▼
        显示 / 写管道
```

### 关键优化点

| # | 改动 | 收益 |
|---|---|---|
| 1 | 接口改 BGR 进 / RGBA 出 | 消除 `dstack`(3.57ms) + `cvtColor`(4.0ms) |
| 2 | 通道转换用 SSSE3 SIMD | 比 numpy 快约 10 倍 |
| 3 | D3D12 资源全程复用 | 消除每帧分配 |
| 4 | 单次提交 + 单次等待 | 从 3 次同步降为 1 次 |
| 5 | 零指导纹理只建一次 | `texZeroMV`/`texZeroDepth` 不再每帧 new |

### 效果

| 分辨率 | 旧路径 | 新路径 | 提升 |
|---|---|---|---|
| 720p | 21.8 ms (46 fps) | **6.65 ms (150 fps)** | 3.3x |
| 1080p | — | **10.80 ms (93 fps)** | — |
| 1440×1440 | — | **10.55 ms (95 fps)** | — |

### 正确性验证(重要)

不能靠"看起来对了"就收工。逐像素比对两条路径:

```
  新宿主 RGBA 输出  ──┐
                      ├──►  np.abs(a-b).mean()  ==  0.0000   ✅
  旧宿主 RGBA 输出  ──┘      max == 0.0  →  完全一致
```

**不是牺牲画质换速度,而是同样的结果用了更少的搬运。**

### 途中踩的坑

| 问题 | 原因 | 解决 |
|---|---|---|
| 链接报 `nvsdk_ngx_s.lib` 找不到 | 系统里没有 NGX SDK | 从官方 `NVIDIA/DLSS` 仓库下载 23 个头文件 + `nvsdk_ngx_s.lib` |
| 头文件互相引用报错 | 只下了部分头文件 | 补齐 `include/` 下全部 23 个 |
| 小分辨率(64×64/128×128)初始化失败 | Feature 18 有最小尺寸要求 | 不测这些尺寸;失败会污染进程,改为"一进程一尺寸"测量 |
| `desc.MipPlanes` 编译错误 | 结构体没有这个字段 | 删掉 |

## 阶段 3：导出管线重构

### 旧导出(`cv2.VideoWriter`)

```
   for 每帧:
       GPU 处理 ──► CPU 转 BGR ──► np.clip 浮点混合 ──► VideoWriter.write()
                                                              │
                                                              ▼
                                                     mp4v 软编码
                                                     (慢, 画质差)
       处理与编码严格串行 ── 两者永不重叠
```

### 新导出(ffmpeg 管道 + 三线程)

```
   ┌────────────┐    ┌──────────────────┐    ┌──────────────┐    ┌─────────┐
   │  主线程    │    │  处理线程         │    │  写线程      │    │ ffmpeg  │
   │  进度轮询  │    │  (GPU 提交/取回)  │    │              │    │ 子进程  │
   └─────┬──────┘    └────────┬─────────┘    └──────┬───────┘    └────┬────┘
         │                    │                      │                 │
         │           cv2.read() → BGR                │                 │
         │                    │                      │                 │
         │           engine.process_rgba()           │                 │
         │           (GPU: Feature 18)                │                 │
         │                    │ RGBA                 │                 │
         │                    ▼                      │                 │
         │              输出视图处理 (可选)           │                 │
         │              view=0 & mix=1.0 → 零转换    │                 │
         │                    │                      │                 │
         │                    └──► write_q.put(bytes) │                 │
         │                       (有界队列 maxsize=4)│                 │
         │                                           │                 │
         │                              write_q.get()│                 │
         │                                           └──► stdin.write()│
         │                                                             │
         │                                              -pix_fmt rgba ─┤
         │                                              NVENC 硬件编码 │
         │                                                             │
         └──► _prog_q.get() 更新进度条 ◄── ("progress", i, n) ◄────────┘
```

**三重并行**:
1. 处理线程与写线程并行 → GPU 计算与管道传输重叠
2. ffmpeg 内部编码与我们的处理并行 → GPU 推理与 NVENC 编码重叠(**不同硬件单元!**)
3. 主线程只做进度显示 → 界面全程不冻结

### 编码器可选(新增 UI 下拉)

| 选项 | 编码器 | 说明 |
|---|---|---|
| H.265 / NVENC | `hevc_nvenc` | 默认,最快,压缩好 |
| H.264 / NVENC | `h264_nvenc` | 兼容性最好 |
| AV1 / NVENC | `av1_nvenc` | 新格式 |
| H.264 / x264 | `libx264` | 软编码备选 |
| H.265 / x265 | `libx265` | 软编码备选(慢) |

### 音轨保留

```
   ffmpeg -i 源视频          ← 输入 1:取音轨(保持原始时间轴)
          -f rawvideo
          -pix_fmt rgba
          -s WxH -r FPS
          -i pipe:0          ← 输入 2:我们喂的处理后帧
          -map 1:v:0         ← 视频来自管道
          -map 0:a?          ← 音频来自源文件(? = 没有也不报错)
          -c:a copy          ← 音轨无损复制
          -c:v hevc_nvenc    ← 硬件编码
```

音轨**原样复制**,不改码率、不重编码,时间轴与源完全一致。

### 实测纯 ffmpeg 吞吐(30 帧 720p,排除 Python)

| 配置 | 耗时 |
|---|---|
| hevc_nvenc p4(无 multipass) | 0.31 s |
| hevc_nvenc p4 + aq + multipass | 0.31 s |
| libx264 veryfast | 0.12 s |

> 编码本身很快 —— 这为阶段 4 的发现埋下伏笔。

### 进度显示:从"第几帧"到"还要多久"

最初的进度只有一句 `导出 123/456`,用户无法判断还要等 1 分钟还是 10 分钟。
现在进度条下方有两行:

```
   [████████████░░░░░░░░░░░░░░░░░░]  40%
   导出 192/480
   速度: 110.5 fps (9 ms/帧)    已用: 0:02    预计剩余: 0:03    预计总耗时: 0:04    总帧数: 480
```

**两个速度用了不同的统计口径,这是刻意的:**

| 指标 | 口径 | 为什么 |
|---|---|---|
| 速度 | 最近 60 帧的滑动窗口 | 反映**当前**状况;若编码器/GPU 变慢能立刻看到 |
| 预计剩余 | 全程累计平均 | **稳定、单调**,不会因为一帧抖动就跳来跳去 |

时间轴从**第一帧真正产出**开始计,这样引擎初始化(~0.5–1 s)和首帧延迟
不会污染估算 —— 否则开头几秒会显示一个荒谬的 ETA。

精度实测(480 帧 @1080p):

| 时刻 | 显示 | 实际 |
|---|---|---|
| t=1.94 s | 已用 0:02,预计剩余 0:03 | 最终总耗时 4.67 s(预测 4 s) |
| 结束时 | 预计剩余 0:00 | ✅ 正确归零 |

显示的"速度"略高于端到端 fps(如 112 vs 103),因为前者只算处理时间、
不含 ffmpeg 收尾。这正是用户需要的信息:**"处理还要多久"**。

> 实现这个小小的功能时,意外挖出了两个能让导出**永久卡死**的 bug
> (mp4 标签不匹配、stderr 管道死锁),详见[经验教训 8](#8-死锁类-bug管道--跨线程--跨解释器)。

## 阶段 4：揪出 Tk 跨线程陷阱

### 症状

导出功能改完后,30 帧 720p 的导出仍然要 **8.06 秒**,而同样的处理循环
脱离 GUI 跑只要 **0.29 秒**。差了 27 倍。

### 排查过程

```
   隔离测试:
   ├─ 纯处理循环 + ffmpeg(无 GUI)      →  0.29 s   ✅ 正常
   ├─ GUI 导出,但禁掉进度回调            →  0.49 s   ✅ 正常
   └─ GUI 导出,保留进度回调              →  8.06 s   ❌ 慢 16 倍
                                                  ▲
                                                  └── 问题锁定在进度回调
```

罪魁祸首:

```python
# 工作线程里 ❌
def worker():
    ...
    if i % 5 == 0:
        self.root.after(0, lambda: self.set_progress(i, n))   # ← 7.57 秒没了
```

### 原因

**Tk 不是线程安全的。** 从非主线程调用 `root.after()`(或任何 widget 方法),
Tcl 解释器会尝试获取内部锁,而主线程正在 `mainloop` 里持有它 ——
产生争用与重试,实测每次调用平均阻塞 **约 1.3 秒**。

### 正确做法:线程安全队列 + 主线程轮询

```
   ┌─────────────────┐                      ┌──────────────────────┐
   │   工作线程      │                      │     主线程           │
   │                 │                      │                      │
   │  ...处理帧...   │                      │  root.after(100, poll)│
   │                 │                      │         │            │
   │  _prog_q.put(   │  ┌────────────────┐  │         ▼            │
   │    ("progress", ├──►  queue.Queue   ├──► _poll_progress()     │
   │     i, n))      │  │  (线程安全)    │  │   读队列 → 更新界面  │
   │                 │  └────────────────┘  │   空了就再排一次     │
   │  _prog_q.put(   │                      │                      │
   │    ("done",...))│                      │  ("done") → 弹完成框 │
   └─────────────────┘                      └──────────────────────┘

   规则: 工作线程【只往队列放数据】,绝不碰任何 Tk 对象。
```

### 效果

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 30 帧导出 | 8.06 s | **0.47 s** |

**17 倍提升,且只是一行代码的架构改动。** 这类"看起来无关紧要"的调用
是性能杀手里最阴险的一种 —— 因为它在小样本下不明显,只有持续调用才暴露。

## 阶段 5：再次测量 —— 发现功耗墙

| 分辨率 | 百万像素 | 耗时 | 每像素 | 帧率 |
|---|---|---|---|---|
| 640×360 | 0.23 | 3.56 ms | 15.43 ns | 281 fps |

| 1440×1440 | 2.07 | 11.33 ms | 5.46 ns | 88 fps |
| 2560×1440 | 3.69 | 18.75 ms | 5.09 ns | 53 fps |

线性拟合:

```
   T(ms) ≈ 2.5 + 4.4 × 百万像素
            ↑        ↑
      固定开销    边际成本
   (同步延迟+     (真实推理

```

- **固定开销 2.5 ms** —— 每帧一次的"提交→等围栏→取回"往返,与小尺寸下的 kernel 启动
- **边际 4.4 ms/百万像素** —— 收敛到约 **5 ns/像素**,说明已接近计算饱和

```
   nvidia-smi 负载采样:
   ┌──────────────────────────────────────────────┐
```

## 阶段 6：双缓冲流水线

### 问题

单槽位模型下,每帧的 CPU 工作(搬运 0.8ms + 录制 0.9ms + 取回 0.9ms ≈ 2.6ms)
**串行叠加**在 GPU 时间(7ms)之后:

```
   单槽位(时间轴):
   ├─ CPU 搬运/录制 ─┤├─ GPU 推理(等待中...) ─────┤├─ CPU 取回 ─┤
   0                2.6                            9.6          11.4 ms
                     ▲                             ▲
                     │                             │
              提交命令后 CPU 就                CPU 一直阻塞在
              在等围栏 ←── 纯浪费              WaitForSingleObject
```

因为只有一个 `texIn`/`texOut`/`readbackBuf`,**上一帧没取回前不能提交下一帧**。

### 方案:两个资源槽 + submit/fetch 两阶段

```
   双槽位(时间轴):
   槽A: ├─ CPU准备A ─┤├─ GPU 推理 A ─────────────┤├─取回A┤
   槽B:              ├─ CPU准备B ─┤├─ GPU 推理 B ──────────┤├─取回B┤
                     ▲            ▲
                     │            │
        提交 A 后不等,立刻开始准备 B   ← CPU 与 GPU 完全重叠
        B 准备完时 A 也快算完了

   稳态吞吐 = max(CPU 每帧 2.6ms, GPU 每帧 7.0ms) = 7.0ms
               而不是 2.6 + 7.0 = 9.6ms
```

### 接口变化

```c
// 新增三个导出
int  dlssnr2_submit(uint8_t* inBgr, int reset);   // 提交,立即返回,不等围栏
int  dlssnr2_fetch (uint8_t* outRgba, uint8_t* outBgr);  // 取回【最旧】的一帧
int  dlssnr2_pending();                           // 在飞帧数
int  dlssnr2_drain();                             // 排空

// 同步接口保留(预览用,一进一出,内部 drain→submit→fetch)
int  dlssnr2_process_rgba(uint8_t* inBgr, uint8_t* outRgba, int reset);
```

### 使用模式

```python
# 导出: 流水线模式
eng.submit_rgba(frames[0], reset=True)      # 预热一帧
for i, fr in enumerate(frames[1:], 1):
    eng.submit_rgba(fr, reset=False)        # 提交帧 N   → 在飞 2 帧
    out = eng.fetch_rgba()                  # 取回帧 N-1 → 在飞 1 帧
    write(out.tobytes())
while (out := eng.fetch_rgba()) is not None:  # 排空最后的帧
    write(out.tobytes())

# 预览: 同步模式(界面必须立刻拿到这一帧)
out = eng.process_rgba(frame, reset=False)
```

### 宿主内部结构

```c
struct Slot {                          // 一套完整的每帧资源
    ID3D12CommandAllocator*   alloc;
    ID3D12GraphicsCommandList* cmd;
    ID3D12Resource* texIn;             // 该槽私有
    ID3D12Resource* texOut;            // 该槽私有
    ID3D12Resource* uploadBuf;         // 该槽私有
    ID3D12Resource* readbackBuf;       // 该槽私有
    uint64_t fenceValue;
    bool     pending;
};

static const int kSlots = 2;           // 双缓冲
Slot slots[2];
int  submitIdx, fetchIdx, pending;

// 共享只读资源(两槽共用,不需要复制)
ID3D12Resource* texZeroMV;             // 全零运动矢量
ID3D12Resource* texZeroDepth;          // 全零深度
```

### 效果

| 指标 | 单缓冲 | 双缓冲 | 提升 |
|---|---|---|---|
| **GPU 利用率** | 87-88% | **98%** | 空隙填满 |
| 720p 单帧 | 6.35 ms (158 fps) | **5.17 ms (193 fps)** | 1.23x |
| 1080p 单帧 | 11.38 ms (88 fps) | **9.53 ms (105 fps)** | 1.19x |
| 1440×1440 单帧 | 11.15 ms (90 fps) | **9.58 ms (104 fps)** | 1.16x |
| 1080p 持续负载 | 92.6 fps | **104.9 fps** | +13% |
| **GUI 导出(1080p)** | 62 fps | **91-94 fps** | **+48%** |
| **GUI 导出(1440×1440)** | 62 fps | **93.7 fps** | **+51%** |

### 正确性验证

```
   16 帧测试:
   流水线输出  ──┐
                 ├──►  mean abs diff = 0.0000,  max = 0.0    ✅
   同步输出    ──┘      →  EXACT (逐像素完全一致)
```

**双缓冲只是改变了时序,不改变任何计算结果。**

## 探索过的分支(未纳入主线)

这些方向做过完整验证,但因为结论或外部限制没有进入主线。记录于此,以免重复投入。

| 分支 | 假设 | 结局 |
|---|---|---|
| A. VSR 三模式 | 用 VFX SDK 加超分/降噪 | 技术可行,但源码丢失 + 收益不如主链路 |
| B. 深度引导 | 喂真实深度改善运动/边缘 | **被证伪**:模型不消费深度输入 |
| C. PySide6 | 更好的界面 | 主动放弃,专注处理链路 |
| D. 三缓冲 | 填掉剩下 2% 的 GPU 空隙 | **被证伪**:吞吐是 max(CPU,GPU),加槽无用 |

> 四个分支里有两个是"证伪"性质的 —— 它们**没有产出代码,但产出了决策**。
> 在优化工作里,能快速判定"这条路不用走"和找到"该走哪条路"同样重要。

### 分支 A：VSR(超分/降噪)三模式

**假设**:用 NVIDIA Video Effects SDK 的 `VideoSuperRes` 效果,给工具加上
RTX Video 超分与降噪两种模式。

**已验证可行的部分**:

- 通过 NGX D3D12 init → `NvCVImage_Alloc(GPU)` → `NvVFX_CudaStreamCreate`
  → `NvVFX_CreateEffect("VideoSuperRes")` 的顺序成功初始化
- 质量档位切换可复用同一 effect(`SetU32` + `Load`),不要 `DestroyEffect`(会挂起)
- 会话池:按输入尺寸缓存会话,换分辨率时新建而非销毁 —— 解决"导出后换视频卡死"

**未纳入的原因**:这部分实现的源码在后续一次目录重置中丢失,且当时的问题是
参数与画质调校,投入产出比不如直接优化主链路的 NR 性能。

### 分支 B：深度引导(Frame Guidance)

**假设**:NR 在零引导(零运动矢量 + 零深度)下,运动区域会拖影。
若喂入真实深度图,NR 应能区分前景/背景,改善边缘与运动。

**实施**:

```
   ┌──────────────────────────────────────────────────────┐
   │  从 Magpie 复用 DepthAnythingV2 (model_fp16.onnx)     │
   │  从 Magpie 复用打包好的 onnxruntime + TensorRT 套件   │
   │  写 depth_host.cpp(onnxruntime C API)               │
   │    • TensorRT EP → 失败(引擎固定 shape,跨分辨率崩) │
   │    • 改用 CUDA EP → 成功                             │
   │  输出 float32 深度图,H×W                            │
   └──────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌──────────────────────────────────────────────────────┐
   │  宿主新增 dlssnr2_set_depth(float* depth, w, h)      │
   │  上传到 R32_FLOAT 纹理,替换 DLSSNR.Depth 绑定        │
   └──────────────────────────────────────────────────────┘
                              │
                              ▼
   ┌──────────────────────────────────────────────────────┐
   │  验证结果:                                            │
   │    set_depth 返回 1(上传成功)                       │
   │    但 NR 输出与深度值完全无关 ——                      │
   │      全零深度 vs 全一深度  → diff 0.0                │
   │      全零深度 vs 随机大值  → diff 0.0                │
   └──────────────────────────────────────────────────────┘
```

**结论**:**该 Feature 18 模型在当前 ProjectID 下锁死为零引导,不消费深度输入。**
这是 NVIDIA 侧的限制,不是接线或格式问题。深度估计管线本身是通的
(深度图质量可辨前景/背景),但 NR 不用它。

### 分支 C：PySide6 界面

尝试过把 tkinter 换成 PySide6(非阻塞预览线程 + 导出对话框 + 进度条)。
后经权衡决定不重构界面,**专注优化处理链路** —— 收益更大、风险更低。
当前保持 tkinter。

### 分支 D：三缓冲(深队列)

**假设**:双缓冲把 GPU 利用率推到 98%,还剩 2% 空隙。
如果加到 3 个资源槽,让更多帧同时在队列里,是否能把那 2% 也吃掉?

**实施**:把 `kSlots` 改成编译期宏,分别构建 2 槽与 3 槽两个 DLL,
在同一台机器上跑同一套 submit/fetch 流水线基准,每个变体独占一个进程
(NGX 核心初始化是一次性的,两个变体不能共存于同一进程)。

**实测结果 —— 吞吐完全一致**:

| 分辨率 | 2 槽 (inflight=2) | 3 槽 (inflight=3) | 差异 |
|---|---|---|---|
| 720p | 182.3 fps | 182.1 fps | -0.1% |
| 1080p | 96.8 fps | 97.1 fps | +0.3% |
| 1440×1440 | 104 fps | 104 fps | ~0 |
| 2560×1440 | 58.4 fps | 58.2 fps | -0.3% |

差异全部落在噪声范围内(<0.5%)。而且尾部延迟也**没有**一致改善:
1080p 时 3 槽的 p99 略好(11.08 → 10.34 ms),但 720p 和 2560×1440 时
反而是 3 槽更差(720p max: 6.22 → 9.46 ms)。

**进一步验证理论**:为确认结论不是"恰好 CPU 太轻",用人造 CPU 负载
把宿主每帧的 CPU 阶段从 2.6 ms 抬到 ~12 ms(远超 7 ms 的 GPU 阶段),
再对比 2 槽 / 3 槽:

| 配置 | 2 槽 | 3 槽 |
|---|---|---|
| CPU 阶段 ~12 ms, GPU ~7 ms | 72.9 fps | 73.0 fps |

**依然完全相同。** 这印证了根本原因:

```
   流水线稳态吞吐 = max( CPU每帧时间 , GPU每帧时间 )

   • 缓冲深度【不能创造吞吐】,它只能【缓冲】吞吐
   • 2 个槽已经足够让"第 N 帧的 CPU 准备"与"第 N-1 帧的 GPU 计算"重叠
   • 第 3 个槽只是让帧在队列里多排一会儿队,GPU 该多快还是多快
   • 该结论对 GPU-bound(CPU<GPU)和 CPU-bound(CPU>GPU)两种情形都成立
```

**额外代价**:

| 项 | 成本 |
|---|---|
| 显存 | 每槽约 33 MB @1080p(RGBA 进 + 出 + 上传暂存 + 回读缓冲),多一槽多 33 MB |
| 延迟 | 端到端延迟增加一帧(导出无影响,实时预览有一帧滞后) |
| 复杂度 | 状态机多一个槽位需要维护 |

**结论**:**保留双缓冲,不采用三缓冲。**
`kSlots` 的编译期宏保留下来(默认 2),这样将来若负载特征改变
(例如换成 CPU 极重的后处理),可以一键重测而无需改代码。

> 这个分支的价值恰恰在于它**被证伪了**。花了不到一小时证明"不需要做",
> 比埋头实现一个更复杂的多缓冲架构要划算得多。

## 经验教训

### 1. 先测量,再动手

阶段 1 和阶段 5 的两次测量,直接改变了优化方向:

- 第一次测出 **CPU 占 34.5%** → 决定重写宿主,而不是去折腾 GPU
- 第二次测出 **CPU 只剩 20%,且功耗墙 Active** → 决定停止"压 CPU",转向时序优化(双缓冲)

**没有测量,就会去优化不重要的地方。**

### 2. 接口设计决定性能上限

旧接口的四个 CPU 指针,从签名上就注定了"数据必须待在 CPU 内存"。
无论 Python 侧怎么写,都绕不开这个往返。
**改 Python 治标,改接口治本。**

### 3. "看起来无关"的调用可能是最大杀手

`root.after()` 从工作线程调用,让 30 帧导出从 0.5 秒变成 8 秒(慢 16 倍)。
这类问题的特征是:

- 代码"能跑",没有报错
- 单次调用开销不明显,只有持续调用才累积
- 跨线程 / 跨语言 / 跨解释器边界是重灾区

**排查方法:开关式隔离(A/B 测试)** —— 把可疑的调用整个禁掉,看差异。

### 4. 正确性验证不能省

每次性能改动后都做逐像素比对:

| 改动 | 验证结果 |
|---|---|
| 换宿主(GPU 直通) | mean abs diff = 0.0000 ✅ |
| 加双缓冲 | mean abs diff = 0.0000 ✅ |

**性能优化最容易的翻车方式,是悄悄改了输出而没人发现。**

### 5. 诚实面对外部限制

深度引导花了大量精力,最终发现是模型不消费深度输入。
**及时用"极端值测试"证伪**(全零 vs 全一 vs 随机值,输出都不变),
比继续调参数更有价值 —— 它给出了一个明确的、不可逾越的边界。

### 6. 区分"我们的开销"和"硬件的开销"

- 我们造成的:CPU 转换、numpy 分配、多次同步、Tk 跨线程 → **全部消除**
- 硬件造成的:推理计算量、功耗墙 → **只能接受或解锁**

把这两者分清楚,才知道什么时候该停手。

### 7. "证伪"和"实现"一样有价值

本项目有两个方向是**被实验否定**的,而它们同样重要:

| 分支 | 否定它的实验 | 省下的代价 |
|---|---|---|
| 深度引导 | 全零/全一/随机深度 → 输出 diff 恒为 0 | 不再纠缠参数调校 |
| 三缓冲 | 2 槽 vs 3 槽吞吐完全相同 | 不做更复杂的多缓冲架构 |

判定"这条路不用走"的关键,是**设计一个能一击证伪的实验**:

- 深度:喂**极端值**(全零 vs 全一 vs 随机大值)。若输出都不变,
  说明输入根本没被读取 —— 这比反复调参数快得多。
- 三缓冲:**同时构建两个变体**,在相同条件下背靠背测量。
  如果连 CPU 人为加重到 GPU 的 1.7 倍都没差别,就可以确定收工。

**能快速证伪,和能快速实现,是同一种能力的两个面。**

### 8. 死锁类 bug:管道 / 跨线程 / 跨解释器

加进度显示这一件"小事",意外挖出两个**能让导出永久卡死**的 bug。
它们的共同特征是:**没有报错、没有崩溃、只是永远不结束**。

#### bug 1:mp4 标签与编码格式不匹配

```python
# 早期写法:从编码器名推导容器标签
tag = "hvc1" if enc.startswith("hevc") else ("av01" if enc.startswith("av1") else "avc1")
```

`"libx265"` **不以 "hevc" 开头**,于是给 HEVC 流打了 `avc1` 标签:

```
-c:v libx265 ... -tag:v avc1      ← 标签说这是 H.264,内容却是 H.265
```

ffmpeg 中途报错退出,而我们的写线程还在往管道里灌数据 → 永久阻塞。
实测:**30 秒零输出**,`msgs=[]`,`size=0`。

**修复**:把标签在编码器表里**显式声明**成三元组 (编码器, 参数, 标签),
不再靠名字猜 —— 名字和格式的对应关系本来就不可靠。
另外在导出循环里加 `proc.poll()` 检测,ffmpeg 提前退出就立刻报错并附上 stderr。

#### bug 2:stderr 管道写满导致死锁

```python
proc = subprocess.Popen(args, stdin=PIPE, stdout=DEVNULL, stderr=PIPE)
# 整个导出过程从不读 stderr
...
err = proc.stderr.read()        # 只在最后读 —— 太晚了
```

x265 即使在 `-loglevel error` 下也会大量打日志(实测单次导出 1.5 KB,但长视频会累积)。
管道缓冲区(约 64 KB)写满后:

```
   x265 阻塞在写 stderr
        ↓
   ffmpeg 停止消费 stdin
        ↓
   写线程阻塞在 proc.stdin.write
        ↓
   有界队列 write_q 填满
        ↓
   处理线程阻塞在 write_q.put     ← 整条流水线静止
```

**修复**:专门的线程持续排空 stderr(限 128 KB 保留尾部用于报错),
并给 x265 加 `-x265-params log-level=error` 从源头减少输出。

#### 这类 bug 的排查方法

关键手法是**把 GUI 变量隔离掉**:

```
   1. 直接跑 ffmpeg 命令行(不用 GUI)          → 成功 → 不是命令行问题
   2. 单轮导出(排除"连续导出")                → 仍失败 → 不是状态残留
   3. 用 subprocess 拦截器打印 GUI 的真实 argv → 发现 -tag:v avc1
                                                 ▲
                                                 └── 一眼看出格式不匹配
```

**第 3 步是决定性的**。不要凭想象重建命令行 —— **把实际用的参数原样打出来**,
错误往往一眼可见。

#### 教训

- **"能用"和"健壮"是两件事**。NVENC 路径一直正常,是因为它日志少、标签对。
  换一个编码器就暴露了两个隐藏假设。
- **测试要覆盖所有分支**。修复后补齐了 5 个编码器的逐项验证,而不是只测常用的那个。
- **任何 PIPE 都必须有人读**。stdout/stderr 都是如此,缓冲区大小是有限的。
- 卡死类 bug 优先怀疑:**管道、锁、跨线程调用**。
